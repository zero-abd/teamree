The window

Three worktrees, four panes, and no question about which one stopped.

Every pane in every worktree carries what it is doing — working, waiting, finished, failed — and how long since it last said anything.

01 — Worktrees

Start five things at once. Keep five checkouts apart.

Add a repository, then start a worktree from any point in its history. Each one is its own checkout on its own branch, so five attempts at the same task never see each other's files — and abandoning one is deleting a directory, not unpicking a commit.

  • Start from a base ref, a local branch, a tag, a commit or a remote branch
  • Created in the background, with progress and a recoverable failure
  • Listed against real git state, not against what teamree last remembered
  • Delete the worktree, and its branch with it if you say so

02 — Terminals

Split the pane. Run the work side by side.

Arbitrarily nested, resizable panes per worktree, with a real PTY behind each one — not an emulated shell and not a log view. At startup teamree looks on your PATH for the agents it knows how to resume — claude, codex, gemini, opencode and droid — and offers what it finds. Anything else you can still type into a pane yourself.

Quitting kills every shell, because a PTY is a child process. What comes back is the part that honestly can: a pane running a coding agent returns with its conversation resumed, because the agent keeps that on disk and teamree remembers which session was in which pane. An ordinary pane returns as a shell in the same directory, and its command is deliberately never re-run.

03 — The CLI

A surface an agent can actually hold.

teamree talks to the running app over a local socket, so an agent can create a worktree, open a terminal, run a command and read the output back — and the window reflects all of it live, because both ends meet at the same runtime rather than at a transport.

Every command takes --json and emits exactly one JSON document on stdout, with errors on stderr and exit codes that mean something: 0 success, 1 the command failed, 2 you typed it wrong, 3 nothing is running to talk to. If the app is not running the CLI says so and exits 3, rather than hanging. 

teamree worktree create --project app --name "fix login"
teamree worktree wait fix-login
teamree terminal run --worktree fix-login --command "npm test"
teamree worktree changes fix-login --json

04 — Teamwork

Watch a teammate's pane. Answer the prompt it is stuck on.

A teammate's worktrees appear in your sidebar. You can read what one of their panes is doing and type into it — which is usually one character and a return, because the thing that stopped an agent at 2am is a question.

Adding a teammate's key lets them run commands on your machine, as you. That is the capability, and it is worth stating plainly: a public key committed to .teamree/members/ is a standing permission for as long as it is in the repository, and there is no per-request grant to approve. It is a capability rather than a permission model, and it is built so that it cannot be used invisibly — the pane says it is being watched and by whom, typing is attributed live, and every remote write is recorded on your machine with who and when. Mute is instant and yours, but it is a per-pane opt-out after the fact rather than a gate before it. Add the keys of people you would hand an unlocked laptop to.

Every guard that makes typing into somebody else's terminal survivable sits at the owner's end: their machine refuses unless your key is on the roster, refuses outright when they have muted the pane, caps one write, and records who typed how much into which pane in a log that survives a restart.

What it takes to set up. None of this is inside the app alone:

  • A git repository you can both push to, cloned by each of you, with an origin remote — push access is membership
  • A relay your team deploys, its wss:// URL committed to .teamree/relay
  • Each person's public key committed to .teamree/members/<handle>.pub and pushed — written is not enough
  • Node 20 or newer, a Cloudflare account and one browser sign-in, on whichever machine deploys the relay

Trying teamwork is the walkthrough in order, with what you should see after each step. 

teamree team status app          # on? who is connected? which relay?
teamree team members app         # the roster, as the repository records it
teamree team watch app ana --follow
teamree team type app ana --text y --enter
teamree team write-log            # every remote keystroke, kept

The relay

Two machines behind two routers cannot reach each other.

So both dial out to a small relay that splices their connections together and is never trusted with what crosses it. A team runs its own, as a Cloudflare Worker. The installed app carries the Worker with it, so it is one command from any directory and needs no clone of the repository — given the three things that command assumes: 

/Applications/teamree.app/Contents/Resources/relay/teamree-relay deploy

It assumes Node 20 or newer on that machine — macOS ships none, and the wrapper exits saying so — a Cloudflare account, and a browser sign-in the first time. It writes the Worker project into ~/teamree-relay, deploys it to your team’s own Cloudflare account and prints the wss:// URL to commit. One person does it once, for the team.

And the rest of it

Parallel work needs somewhere to put it. Then it needs answering for.

Five agents running at once create one question that git status cannot answer: which of them has stopped, and which one stopped on you.

Which agent needs you

Every pane in every worktree shows what it is doing — working, waiting, finished, failed — and how long since it last said anything. It is deliberately a narrow reading: teamree watches a PTY, not an agent's protocol, so “waiting” means the output stopped, not that the agent asked you something.

All of them at once

One view lists every pane in every worktree, ordered by what would make you look: failures first, then work in progress, then waiting, then finished — and within each, the one that has been silent longest. Counts per state sit above it, and a row takes you to that pane.

A live picture of the work

Status per worktree, updated by watching the checkout rather than by polling, so an edit made by an agent inside a ten-minute shell session moves the chips immediately. A panel shows the changed paths and the patch for any of them.

Enough git to finish

See what changed, tick what should go in, commit it, and check whether the branch would merge into its base — answered in memory, so asking costs the repository nothing. Push when it is ready. There is no force push and no flag to ask for one.

Where it actually is

Built and used; not yet worn in.

This is the first release, and it is worth being exact about what that means rather than letting you find out.

Platform
macOS only, one universal .dmg — a decision rather than a gap waiting to close. Linux was packaged and launched for real before the build matrix narrowed; the Windows packaging has never been built by anybody, and nobody should download this expecting it to arrive.
Signing
Unsigned, ad-hoc only. The packaging will sign and notarize the moment a Developer ID is put in front of it; nobody has one yet.
Single-user
Done. Worktrees, terminals, status, git and the CLI are built and under test.
Teamwork
Built, not weathered. All five stages have landed — identity, the relay and presence, watching a pane, typing into one, staleness. Two Macs in two places is the one thing still untested.
Price
Free. The source is on GitHub and so is the roadmap, including the known gaps — recorded rather than discovered.
Bring your own agent
teamree is a place to run agents, not another one. It looks on your PATH for the five it knows how to resume — claude, codex, gemini, opencode, droid — and offers what it finds.

Installing

First launch, and the one command it needs.

teamree is not notarised, so macOS asks you to confirm the first launch. This is what it says, what to press, and the command that settles it for good.

What macOS shows you, and what to do

teamree has no Apple Developer certificate behind it, so the build you just downloaded is unsigned. The first time you open it, macOS refuses — with a dialog whose two buttons are Move to Trash and Done:

“teamree” Not Opened
Apple could not verify “teamree” is free of malware that may harm your Mac or compromise your privacy.

Do not press Move to Trash. It is the prominent button and it is the wrong one — it deletes the app you just downloaded. Press Done.

Nothing has been found wrong with teamree. macOS has not examined it and detected something; it is telling you the file arrived without a certificate naming who built it, so Apple has never seen it and cannot vouch for it either way. What the missing signature actually costs you is the guarantee that the file was not altered on its way here — and a checksum gives you that by another route, which is why every release publishes one.

  1. Open the .dmg and drag teamree to Applications. There is an Applications shortcut in the window to drag onto, and no licence to agree to.
  2. Open it, get the dialog above, and press Done.
  3. Clear the quarantine flag, once. Every file a browser downloads is marked with com.apple.quarantine; removing it tells macOS this is a file you put there on purpose. 
    xattr -dr com.apple.quarantine /Applications/teamree.app
  4. Open it normally. It will not ask again.

There is no “Open Anyway” button in that dialog. Through macOS 14 you could Control-click the app and choose Open; macOS 15 removed that, and on 15 and later — macOS 26 included — the dialog offers no way through at all. If you would rather not type a command, the button does exist, just elsewhere: after pressing Done, go to System Settings → Privacy & Security and scroll to the Security section, where a line naming teamree appears with Open Anyway beside it. Expect it to ask for your password or Touch ID.

Being exact about that last paragraph, because the rest of this is written from watching a real download install itself: the command above was run against this build and watched to work, the dialog is quoted off the screen, and Done was pressed on it and dismissed it. The System Settings route was not clicked through. Open Anyway is the button macOS ships for this case, but nobody here has confirmed how that pane looks on macOS 26 with teamree in it. If you take that route and it does not match, the command is the one that was tested.

Two silences that look like something worse than they are. Before you clear the flag, open teamree.app from a terminal prints nothing and exits 0, and the app still does not start. The bundled teamree CLI is killed outright — no stdout, no stderr, exit status 137. Neither is a broken build; both are this.

And one thing that will look like failure afterwards. spctl -a -vv says rejected before you clear quarantine and after. Clearing the attribute removes what makes macOS enforce the check; it does not give the app a signature, and nothing short of a Developer ID will make spctl say accepted. The app opens regardless. If you went looking for a way to confirm the fix worked, open the app — do not ask spctl.

Check the download against the release. Compare the output of this against the digest printed below. If they agree, the file you have is the file the build produced. (SHA256SUMS.txt is published beside the .dmg and carries the same digest, listed under the release's versioned file name.) 

shasum -a 256 teamree-mac-universal.dmg

SHA-256 ccf09c74af6ba75a032fee58b11dc578ece77dd3ec38401328fe34a8131bf8d2

The macOS builds are signed, but only ad-hoc — a signature with no identity attached, which is the floor Apple Silicon needs to execute a binary at all. It is not a Developer ID, it is not notarised, and the .dmg itself is not signed at all. The full account, including what codesign prints if you check, is in docs/install.md.
